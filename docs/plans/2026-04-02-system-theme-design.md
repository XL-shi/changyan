# 系统主题跟随与暗色可读性设计

## 背景

在另一台启用深色模式的 macOS 设备上，应用内多处按钮文字在黑色背景下对比度不足，出现“按钮存在但文案看不清”的问题。当前项目虽然支持 `light` / `dark` / `system` 三种主题配置，并且默认值为 `system`，但仍有不少交互样式直接写死了 `text-white`、`bg-accent`、透明按钮前景色等局部样式，导致主题切换后的可读性不一致。

用户已明确本次目标：

- 整个应用以后只跟随操作系统明暗主题
- macOS 和 Windows 都按系统深浅色自动切换
- 删除应用内手动主题切换入口
- 全面检查按钮、输入框、选择器和关键交互区域，修复深色模式下文案不可读问题

## 目标

1. 前端运行时只依据系统主题决定明暗，不再提供应用内手动切换
2. 深色模式下主按钮、次按钮、透明按钮、输入框、下拉框和浮层操作具备稳定可读性
3. 保持现有整体视觉语言，不做超出需求的 UI 重构
4. 对已有本地配置保持兼容，避免因历史 `theme` 值导致运行异常

## 非目标

- 不重做整套品牌色或设计语言
- 不引入完整的全局 Button 组件体系
- 不处理 Windows 强调色、高对比度等额外系统外观能力
- 不在本次移除存储层中的 `theme` 字段，只先移除 UI 与运行时分支依赖

## 方案比较

### 方案 A：保留三态主题，仅修补有问题样式

优点：

- 改动最小
- 实现速度快

缺点：

- 与“只跟随系统主题”的目标不一致
- 继续维护无用的主题分支
- 后续仍可能出现新页面继续写死颜色的问题

### 方案 B：统一为仅跟随系统主题，并收敛关键交互样式

优点：

- 与目标完全一致
- macOS / Windows 行为统一
- 运行时逻辑更简单，后续维护成本更低

缺点：

- 需要同步清理设置项、主题逻辑和部分测试
- 需要对多处按钮类名做一次系统性收口

### 方案 C：同时做系统主题 + 组件级按钮抽象重构

优点：

- 长期最整洁

缺点：

- 明显超出本次范围
- 改动面大，回归风险更高

## 推荐方案

采用方案 B。

原因：

- 直接满足用户目标
- 比方案 A 更彻底，但又避免方案 C 的过度工程化
- 可将本次问题收敛为“系统主题驱动 + token 化样式修复”，而不是发散成整站 UI 重构

## 详细设计

### 1. 主题策略

保留浅色和深色 token，但运行时不再读取用户手动选择的 `light` / `dark` 值，只根据 `window.matchMedia('(prefers-color-scheme: dark)')` 控制根节点是否带 `dark`。

这意味着：

- macOS 浅色 -> 应用浅色
- macOS 深色 -> 应用深色
- Windows 浅色 -> 应用浅色
- Windows 深色 -> 应用深色

主题相关设置入口会从设置页移除，避免用户误以为还能手动控制应用主题。

### 2. 配置兼容策略

考虑到已有用户本地配置中可能仍保存 `theme: 'light' | 'dark' | 'system'`，本次不做激进迁移。

兼容原则：

- 旧配置继续允许被读取
- 运行时忽略旧值，统一按系统主题渲染
- 保存配置时不再暴露主题设置入口
- 若类型定义仍保留 `theme` 字段，则先作为兼容字段存在

这样可以避免影响已有存量用户数据和 Rust 存储行为。

### 3. 样式收敛范围

本次重点检查并修复以下区域：

- `Onboarding`：关闭、跳过、上一步、下一步、连接测试按钮
- `Settings`：热键按钮、权限相关按钮、测试按钮、输入框、下拉框、保存栏
- `History`：搜索框、清空按钮、复制按钮
- `Account` / `Upgrade` / `Dictionary` / `Stt` / `Llm` / `Scenes`：主 CTA 和次级操作按钮
- `CopyDialog` 等弹窗或浮层中的主要按钮

修复原则：

- 优先移除写死的 `text-white` / `text-black` / `bg-white` / `bg-black`
- 尽量复用现有 token 与统一样式类，如 `jelly-btn`、`jelly-btn-accent`
- 对“固定深色视觉”的特殊区域单独保留，但确保文本对比度足够

### 4. 样式策略

针对当前代码中的几类问题，分别采用不同处理方式：

- 主按钮：统一收敛到 `jelly-btn-accent` 或等价 token 组合，确保浅色下深底浅字、深色下浅底深字
- 次按钮：使用 `jelly-btn` 或基于 `bg-bg-secondary` / `text-text-primary` / `border-border` 的主题 token 组合
- 透明图标按钮：使用 `text-text-tertiary` 作为默认前景，hover 后切换到 `text-text-primary` 或语义色
- 输入框 / 下拉框：统一使用 `bg-bg-secondary`、`text-text-primary`、`border-border`、`focus:border-border-focus`
- disabled 态：保留禁用感，但不能通过降低透明度到不可读

### 5. 测试策略

本次以“关键交互面在系统浅色/深色下都保持可读”为主要验收标准。

自动化验证重点：

- 与主题或设置状态相关的 store / settings 测试
- `History` 等已存在测试文件的断言更新
- 必要时补充 `useTheme` 或设置页行为测试，覆盖“只跟随系统主题”的逻辑收敛

人工验证重点：

- macOS 深色模式下按钮与文案可读性
- 系统切换浅色/深色时应用能同步更新
- Windows 跟随系统深浅色行为不回归

### 6. 风险与缓解

风险：

- 某些页面仍存在遗漏的写死颜色
- 删除主题设置入口后，现有测试或文案可能失效
- 个别固定视觉区域可能被误改，导致原有效果退化

缓解：

- 通过搜索全局 `text-white` / `bg-accent` / `text-black` 等模式做清点
- 只对“交互可读性”相关区域做收敛，不顺带重排版
- 修改后运行 TypeScript、Vitest 和相关 lint 检查

## 结论

本次设计采用“只跟随系统主题 + 收敛关键交互样式”的方案，目标是在不做大规模 UI 重构的前提下，解决深色模式下按钮和文字的可读性问题，并统一 macOS / Windows 的主题行为。
